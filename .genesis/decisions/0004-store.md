# ADR 0004 — The forgetting engine: what proves a memory was forgotten, how `forget` composes with `decay`/`contradict`, who owns ADR 0003's precondition, and four other design questions this milestone's brief posed directly

- **Date:** 2026-09-22
- **Status:** accepted
- **Phase / milestone:** M5 (BUILD) — `lib/store/`

## Context

`memory-plan.md` §4 names this milestone "the centre of this project's entire brief": *"Source, confidence, freshness, scope, and an explicit forgetting policy... plain vector RAG is a disqualifier."* `PLAN.md`'s M5 row requires `forget(memory, reason, now)` producing a real `TombstonedMemory` + `Tombstone` pair, and `BeliefQuery` — the read path that structurally cannot construct a `believed`/`doubted` answer from a tombstoned record. `lib/contracts/**`, `lib/decay/**`, and `lib/contradiction/**` are frozen; this milestone builds `lib/store/**` only, on top of all three. This ADR records the five design questions this milestone's own brief posed directly, plus two implementation-level decisions (the `forget` overload shape, and `TombstoneId` minting) that fell out of trying to make the plan's own literal sketches actually compile — the same category of correction M1's ADR made for `Memory.status`/`Tombstone.supersededBy`.

## Decision 1 — WHAT PROVES A MEMORY WAS FORGOTTEN: two parts, and what a caller can PROVE versus what they must TRUST

`memory-plan.md` §4 names two required parts. Both are real here, and this section states plainly where the line between "proven" and "trusted" actually falls — the same discipline this account's own standing note ("don't restate limits more strongly than they're true," and its mirror, don't understate them either) asks for.

**Part 1 — the record.** `forget()` (`forget.ts`) returns a real `TombstonedMemory<TValue>`: every field the original `Memory` carried, byte-for-byte (`__tests__/forget.test.ts`'s "preserves every other field" test proves this with a direct object comparison, not a shape assertion), plus a `Tombstone` naming the reason and — for `"contradicted"`/`"superseded"` — exactly which memory won. This is PROVEN, not trusted: given any `TombstonedMemory`, a caller can read `.tombstone.reason` and (where applicable) `.tombstone.supersededBy` directly, with no appeal to an external log. The type system enforces the "iff" (M1's `CausedTombstone`/`UncausedTombstone` split) and this milestone's own overloaded `forget` signature (Decision 5, below) enforces it again at the one call site that constructs a `Tombstone` at all.

**Part 2 — the query-time guarantee.** `queryBelief()` (`belief-query.ts`) cannot accept a `TombstonedMemory` in its `candidates` parameter at all (`Memory<TValue>`'s three-member `status` union excludes `"tombstoned"` — M1's own Decision 2) — PROVEN at compile time, `__tests__/belief-query-refusal.test.ts`'s `@ts-expect-error` proof against the REAL function (not M1's stand-in). Given a corpus whose only candidates for a subject are tombstoned, `queryBelief` returns `{status: "unknown", reason: "all-known-memories-tombstoned", tombstones: [...]}` — PROVEN directly, `__tests__/belief-query.test.ts`'s dedicated test, never inferred from "it didn't crash."

**What a caller must still TRUST, stated plainly, not glossed over:**

1. **That the `now` a caller supplies to `forget`/`queryBelief` is honest.** Neither function reads a real clock (`memory-plan.md`'s own purity discipline, matching `decay`/`contradict`); both take `now` as an argument and trust it. A caller who lies about `now` gets an internally-consistent but factually wrong answer — the same trust boundary `lib/decay`/`lib/contradiction` already disclose for their own `now`/`believedAt` inputs.
2. **That the caller's grouping of `candidates`/`tombstones` by `(subject, predicate, scope)` is correct.** `queryBelief` never reads `.subject`/`.predicate`/`.scope` to filter its own input — it trusts whatever set it is handed represents one query's worth of live/forgotten candidates (`belief-query.ts`'s own header, "PRECONDITION" section). A caller that mis-groups gets an answer about whatever it actually handed in, not a wrong answer about what it meant to ask.
3. **That a `Tombstone`'s own `reason` was assigned honestly at the moment `forget` was called** — e.g., that a caller invoking `forget(m, "source-revoked", now)` genuinely observed a revocation, not merely wanted a memory gone. `lib/store/**` provides the MECHANISM (a typed, closed reason, never free text — M1's own `ForgetReason`) and proves each mechanism fires; it cannot, and does not claim to, verify the CALLER's own honesty about which real-world event triggered the call. This is the same boundary `agent-trust-layer`'s own revocation-check machinery draws between "the check is real" and "the underlying registry is honest."

## Decision 2 — DOES `forget` COMPOSE WITH `decay`/`contradict`, OR DUPLICATE THEIR LOGIC? — COMPOSE, PROVEN BY WHAT `lib/store/**` DOES NOT CONTAIN — REVISED AFTER INDEPENDENT REVIEW

**This decision's first pass was wrong on one outcome, and is recorded here as revised, not silently corrected — the earlier reasoning was internally coherent and still produced the wrong answer, which is a worse failure than an unconvincing one (the identical framing ADR 0003's own Decision 6 uses for its own revision).**

`lib/store/**` contains no decay curve and no value-comparison logic. Two concrete compositions, both load-bearing, both exercised by real tests:

1. **`age-exceeded`, lazily, at query time.** `.genesis/decisions/0002-decay.md`'s own forward note for M5: *"`decay(memory, now).status === 'forgettable'` is the signal to call `forget(memory, 'age-exceeded', now)` — `lib/decay` never does this itself."* `belief-query.ts`'s `partitionByDecay` is exactly that composition — see Decision 3 below for why it runs on every call rather than as a separate maintenance step. `__tests__/belief-query.test.ts`'s "composes decay" block proves a live memory at exactly its `forgetFloor` is converted to a real, freshly-minted `Tombstone` (not merely excluded from the answer) and reported. This half was correct in the first pass and is unchanged.
2. **`contradicted`/`superseded`, via a live `contradict()` call.** `queryBelief` never trusts a stored `Memory.status` field to decide the answer — it calls `contradict(older, newer)` itself, ordered by `believedAt` (`contradict`'s own anti-symmetry requirement, ADR 0003 Decision 3), and answers from THAT outcome.

**The first-pass mistake, on `contradict`'s `"superseded"` outcome specifically.** The first pass answered `"disputed"` for `"superseded"` exactly as it did for a genuine `"disputed"`/`"not-comparable"` outcome, reasoning that `BeliefAnswer`'s frozen `"believed"` variant has nowhere to carry the tombstone a real resolution would produce, so reporting `"believed"` and silently discarding that tombstone would be dishonest. **That reasoning solved the wrong problem.** It treated "where does the tombstone go" as a reason to withhold the CORRECT answer, when the actual fix was to give the tombstone somewhere to go — not to hide the answer. `memory-plan.md` §8's own demo moment is EXACTLY this case (two same-tier `direct-avowal` memories, the newer disagreeing — ADR 0003's own worked contrast, Decision 6), and its own text is unambiguous: *"the system answers with the new address, reports that the old one is no longer surfaced as belief... and produces the tombstone."* Answering `"disputed"` here shows a judge two addresses side by side on the one screen this project exists to get right — independent review caught this directly against the plan's own demo text, not against an abstract principle.

**Chosen (revised): `queryBelief`'s own RETURN TYPE carries the answer.** `BeliefQueryResult<TValue> = { answer: BeliefAnswer<TValue>; newlyForgotten: readonly Tombstone[] }` — a small, LOCAL wrapper (not a change to `lib/contracts`' frozen `BeliefAnswer`). On `"superseded"`, `queryBelief` now composes `forget(older, "contradicted", now, newer.id)` right there — the SAME lazy-at-query-time pattern already established for a decay-forgettable candidate (Decision 3 below is the direct precedent, not a new kind of side effect invented for this one case) — and answers `"believed"`/`"doubted"` on `newer`, with the loser's fresh tombstone reported in `newlyForgotten`. `"disputed"` and `"not-comparable"` still collapse to the SAME `BeliefAnswer.disputed` variant (see the file header's own disclosure of that specific, narrower collapse, and Decision 2a below) — but `"superseded"` no longer shares that treatment, because `contradict` itself DID commit to a verdict for it, and reporting anything other than that verdict would be the store overriding an engine it is supposed to defer to.

**Why "confidence dropped to zero the instant the new one arrived" (`memory-plan.md` §8's own phrase) is STILL surfaced, never rewritten, under the revised design.** M1 split `Memory.confidence` (recorded, immutable) from `effectiveConfidence`/`queryConfidence` (computed) specifically so this sentence could be literally true without ever touching a record. Tombstoning `older` — even lazily, even at query time — makes `queryConfidence(olderAsTombstoned, now)` report exactly `0`, unconditionally, by the SAME frozen mechanism every other `TombstonedMemory` already gets (`lib/decay/query-confidence.ts`'s own tombstoned-branch check). `__tests__/belief-query.test.ts`'s dedicated §8-shaped test proves this directly, composing `queryConfidence` rather than re-deriving the claim.

## Decision 2a — `"disputed"` vs. `"not-comparable"`: kept collapsed to one `BeliefAnswer` variant, and this is now the ONLY collapse left, stated as a disclosed limit rather than left to be discovered by grep

With `"superseded"` no longer folded in, `queryBelief`'s two-or-more-candidates branch still answers the SAME `BeliefAnswer.disputed` variant for two of `contradict`'s four outcomes: a genuine `"disputed"` (neither side has a decisive verdict — a real, mechanically-produced non-outcome) and `"not-comparable"` (`contradict` refused to compare at all — a caller-precondition violation under this function's own documented contract, e.g. a `believedAt` tie). **This narrower collapse is kept, deliberately, and named as a real limit, not fixed:** `BeliefAnswer.disputed`'s only payload is the two-candidate tuple (`belief-answer.ts`, frozen) — there is no field to carry `NotComparableReason` even if this function wanted to, and `BeliefAnswer` cannot be widened by this milestone. Both facts share the one property that actually matters to a caller — "no side has a decisive verdict, and nothing was tombstoned" — which is a materially different situation from `"superseded"` (where a verdict EXISTS and something MUST be tombstoned to report it honestly). Unlike the `"superseded"` mistake above, there is no available fix within this milestone's own frozen boundaries: reporting `"not-comparable"` distinctly would require either reopening `lib/contracts` (unauthorized, out of scope) or inventing a second, non-`BeliefAnswer` return channel for it (which would then need its own justification for why `"disputed"`'s own reason isn't in `BeliefAnswer` either — the honest answer is that `memory-plan.md`'s own plan never asked for one). Recorded here explicitly so a future reader finds this collapse documented rather than inferred.

**Neither `decay`'s curve arithmetic nor `contradict`'s tier-split/value-comparison logic is reimplemented anywhere in `lib/store/**`** — `git grep -n "0.5 \*\*\|Math.pow(0.5"` and `git grep -n "tier ==="` both return nothing under `lib/store/`, confirmed directly rather than merely claimed.

## Decision 3 — ADR 0003's PRECONDITION IS NOW MINE: the reduction was NOT sound, and this store enforces it, on every call, not via a separate maintenance step

`.genesis/decisions/0003-contradiction.md`, Finding 2, left this open: *"'older is still inside its freshness window' reduces, in practice, to 'older is still a live `Memory<TValue>`'... If this reduction turns out to be wrong once M5 exists for real... that is M5's finding to make, with a real case in hand."*

**The finding, with a real case in hand: the reduction is NOT sound in general.** `decay()` has no side effect (`lib/decay/decay.ts`'s own header: "has no side effect and does not construct a `Tombstone`"), so a `Memory` can remain structurally "live" — un-tombstoned — for however long nobody happens to call `forget` on it, regardless of what its own decay curve says. "Still live" and "still fresh" are the same fact ONLY if something enforces that a live memory is forgotten the instant it crosses its `forgetFloor`. Nothing built before this milestone enforces that.

**Ruling: my store enforces it, and enforces it INSIDE the one function whose own correctness actually depends on it, on EVERY call — not via a separate `sweepDecayed`-style maintenance function a caller might forget to run first.** `partitionByDecay` (`belief-query.ts`) is the literal first thing `queryBelief` does to its `candidates` argument; the two-or-more-candidates branch that calls `contradict` only ever sees elements of `fresh`, never a raw, unswept candidate. This makes the freshness precondition TRUE BY CONSTRUCTION at the call site that needs it, rather than documented and hoped for.

**Alternative considered and rejected: a standalone `sweepDecayed(candidates, now)` function, called by convention before every query.** Rejected for the same reason this account's own standing note treats a stated-but-unenforced constraint as a real risk (`Tombstone.supersededBy`'s own M1 history is the precedent): "the caller is expected to run this first" is a discipline, not a guarantee, and the one function whose correctness actually depends on freshness should not depend on a second function nothing forces anyone to call.

## Decision 4 — CAN A TOMBSTONE BE UN-TOMBSTONED? — NO; A REINSTATEMENT IS ALWAYS A NEW MEMORY, NEVER A RESURRECTION

**No `unforget`/`resurrect` operation exists anywhere in `lib/store/**` — its absence is itself the decision, not an oversight.** If a revoked source is later reinstated, or a contradiction is itself later contradicted (a `derived-inference` that loses a dispute is later confirmed correct by a fresh `direct-avowal`), the honest representation is a **brand-new `Memory`** — a new `id`, a new `believedAt`, entering the corpus exactly the way any other newly-affirmed belief would, competing (via `contradict`, at whatever future query needs to compare it) against whatever is currently live. The `TombstonedMemory`/`Tombstone` that recorded the ORIGINAL forgetting stays exactly as it was: an honest, permanent record of "this WAS believed, and here is why it stopped being."

**Why, argued from the type system this project already committed to, not merely from house style:** `Tombstone` (`lib/contracts/tombstone.ts`, frozen) has no field an "un-tombstone" operation could even target — every field is `readonly`, and a `TombstonedMemory`'s `status: "tombstoned"` literal is not a member of `Memory.status`'s union it could be reassigned into without constructing an entirely new object anyway (M1's own Decision 2 — this is the SAME structural fact that makes the compile-time query refusal possible in the first place). "Un-tombstoning" a record in place would require either mutating a `readonly` field (impossible without a cast that defeats the type system, the same category of gap `json.ts`'s own "KNOWN LIMITATION" already discloses and does not pretend to close) or constructing a new `Memory` from the tombstoned one's fields — which is just... constructing a new `Memory`. There is no third operation hiding between those two; giving it a name (`resurrect`) would suggest a capability this store does not, and should not, have.

**Consistency with §4's append-only design, stated once more because it is the point:** `memory-plan.md` §4: *"Deletion is deliberately not offered as an option in this design... the brief asks for a system that knows it might be wrong, which requires it to remember that it forgot something."* Allowing a tombstone to be reversed in place would create exactly the failure mode deletion creates — a record whose history could be edited after the fact — one layer removed. A caller who wants "the store now believes X again" gets that fact by making a new claim, honestly dated, which itself becomes part of the permanent record; the OLD tombstone remains, forever, exactly what it always was: proof that between one moment and another, this store did not believe X.

## Decision 5 — SCOPE-EXITED: the trigger is deliberately left unspecified by this milestone, matching the discipline M1 already established for `Provenance.tier`'s mapping

**The plan's own admission: this is "the reason with the least specified trigger."** `memory-plan.md` §4 names the EVENT informally ("the bounded context this memory lived in closed — account deleted, session ended") but never specifies WHO detects that event or HOW. This milestone does not invent a scope registry, an account-lifecycle listener, or any machinery to detect a scope closing — `forget(memory, "scope-exited", now)` is a plain, direct call, proven to tombstone correctly in isolation (`__tests__/forget.test.ts`), and that is the entire mechanism this milestone builds.

**Why not build a registry:** the identical shape of decision M1's own ADR made for `Provenance.tier`'s `SourceKind` mapping (`.genesis/decisions/0001-contracts.md`, Decision 1): "Whoever needs it first should decide it with a real case in hand... encoding a guessed mapping into a file on no stated authority beyond one worked example is a worse mistake than leaving the decision to a later milestone with a real case in front of it." M6 (the personal-assistant domain adapter, unbuilt) is the first milestone with a REAL scope-exit trigger to name (a user deleting their account, most plausibly) — inventing a generic "scope registry" here, with no concrete caller, would be exactly the "speculative flexibility nobody asked for" this account's own standing note warns cost a sibling project five bypasses.

## Decision 6 — `forget`'S OVERLOADED SIGNATURE: a correction to `memory-plan.md` §3's literal `(memory, reason, now)` sketch, in the same spirit as M1's own two corrections

`Tombstone` (frozen) is a two-branch discriminated union: `supersededBy: MemoryId` is REQUIRED for `"contradicted"`/`"superseded"`, and its PRESENCE is an excess-property error for the other three reasons. A single flat signature `forget(memory, reason: ForgetReason, now, supersededBy?: MemoryId)` cannot express "required iff caused" at the call site — the exact gap M1's own ADR already closed for the TYPE (`.genesis/decisions/0001-contracts.md`, Decision 3) but which a flat function signature would silently reopen one call away. `forget.ts` declares two overloads (caused: 4 required params; uncaused: exactly 3) so the SAME constraint holds at every call site, proven with `@ts-expect-error` in both directions (`__tests__/forget.test.ts`). A runtime backstop (`isCausedReason`, throwing rather than silently constructing a malformed `Tombstone`) defends the one path a caller could still reach by defeating the overloads with a type cast — belt-and-suspenders, not the primary defence, the same discipline `lib/decay/decay.ts`'s own header describes for its post-validation arithmetic clamp.

**Alternative considered and rejected: a flat signature plus a runtime-only check.** Rejected for the reason above — it would leave the "required iff caused" constraint enforced only at RUNTIME for `forget`'s own callers, one layer below where `Tombstone`'s own type already enforces it, undoing the point of M1's Decision 3 the moment a caller reaches this function instead of constructing a `Tombstone` literal directly.

## Decision 7 — `TombstoneId` MINTING: `Math.random`, not `node:crypto`, and why that is not a downgrade

`lib/contracts/tombstone-id.ts`'s own header left this deliberately unowned: "whoever eventually builds the store (M5/M6) owns *how* the string is generated." This milestone's own architecture test (`__tests__/architecture.test.ts`, copied verbatim per this milestone's brief) forbids every import outside `lib/store/`, `lib/contracts/`, `lib/decay/`, `lib/contradiction/` — `node:crypto`'s `randomUUID` would need an import this test would have to special-case. `mintTombstoneId` (`forget.ts`) uses `Math.random()`/`Date`, plain ES2022 globals needing no import at all, seeded with `memoryId:reason:now` for traceability plus a random suffix for uniqueness. A `TombstoneId` is an opaque audit-trail identity (`tombstone-id.ts`'s own header: "no invariant to validate beyond 'is a string'"), not a security credential — uniqueness, not unpredictability, is the only property this milestone's own success criteria need, and `Math.random` supplies it without touching this milestone's own frozen import boundary.

## Consequences

- Positive: the query-time guarantee (§4's falsifiability test) and the compile-time refusal (M1's own success criterion, restated for M5) are BOTH proven directly against the real, shipped functions — not a stand-in, not an assertion.
- Positive: `lib/store/**` reimplements nothing from `lib/decay`/`lib/contradiction` — every freshness and disagreement judgment is a real call into the frozen engine that owns it.
- Positive: the ADR 0003 precondition question this milestone was explicitly handed is answered with a real case, not deferred again.
- Positive, closing what was flagged as this milestone's own weakest point in its first build report: `queryBelief` now answers `memory-plan.md` §8's own demo moment CORRECTLY — a same-tier `direct-avowal` supersede resolves to `"believed"` on the new value, with a real tombstone naming the old one and its confidence provably reading as zero, proven directly in `__tests__/belief-query.test.ts`'s dedicated §8-shaped test block, not merely asserted to be fixed.
- Negative / cost, disclosed and now narrower than the first pass's own finding: `queryBelief`'s two-or-more-candidates branch still answers the SAME `BeliefAnswer.disputed` variant for `contradict`'s `"disputed"` AND `"not-comparable"` outcomes (Decision 2a) — a real, permanent limit of `BeliefAnswer`'s own frozen shape (no field to carry `NotComparableReason`), not something this milestone can close from inside its own boundary. `"superseded"` no longer shares this collapse.
- Negative / cost, disclosed: `queryBelief`'s precondition (at most two fresh candidates per query) is trusted, not verified against `(subject, predicate, scope)` grouping — a defensively-oversized input (3+) is handled without crashing (the two most-recently-believed win, the rest are silently excluded from the answer) but this is a disclosed fallback, not a claim that three-way disputes are meaningfully supported.
- Negative / cost, newly introduced by this revision: `queryBelief`'s return type is no longer bare `BeliefAnswer<TValue>` — it is `BeliefQueryResult<TValue>` (`{ answer, newlyForgotten }`). Every caller (M6's domain adapter, M8's UI) must unwrap `.answer` rather than reading the result directly as a `BeliefAnswer`. This is a real API surface cost, accepted because the alternative (silently discarding a tombstone `memory-plan.md` §4 says must exist) is worse, and because `BeliefQuery`'s own exact return shape was never pinned by the plan beyond "the read path" — M5 owns deciding it, same authority M1's ADR used for its own two corrections.
- Forward note for M6: no `affirm`/write-path orchestration exists in `lib/store/**` — this milestone's own success criteria ask for `forget` and the read path only (`PLAN.md`'s M5 row). `queryBelief`'s own lazy resolution of a live `"superseded"` detection is a defensive backstop for exactly the race `memory-plan.md` §10 describes, not the PRIMARY mechanism — in a well-formed store, M6's write-time `affirm` should call `contradict`+`forget` synchronously when a new memory is written, so a query rarely if ever needs to resolve a supersede lazily at all.
- Forward note for M7: the two same-tick-race mechanics `memory-plan.md` §10 names (an `affirm` interleaved with a query; a clock-inconsistent tie) are NOT separately tested by this milestone beyond what `queryBelief`'s own "composes contradict() live" tests already cover incidentally — M7 owns constructing the dedicated interleaving test `§10(a)` describes. This milestone's own lazy-supersede-resolution IS a real, tested answer to part of that race (the query never returns a stale `"believed"`), but M7 should verify it under real concurrent interleaving, not just the sequential calls this milestone's own tests make.

## Alternatives rejected (summary, cross-referenced above)

- Answering `"disputed"` for a live-detected `"superseded"` outcome (Decision 2, this milestone's OWN first pass) — internally coherent reasoning that nonetheless broke `memory-plan.md` §8's own demo moment; revised after independent review checked the first pass directly against the plan's own demo text.
- Reporting `"not-comparable"` as its own distinct `BeliefAnswer` variant (Decision 2a) — `BeliefAnswer`'s frozen shape has no field for it, and this milestone has no authority to widen `lib/contracts`.
- A standalone `sweepDecayed` maintenance function instead of enforcing freshness inside `queryBelief` itself (Decision 3) — a discipline, not a guarantee.
- An `unforget`/`resurrect` operation (Decision 4) — the type system already refuses it structurally, and offering one anyway would recreate deletion's own failure mode one layer removed.
- Inventing a scope-exit registry/trigger mechanism (Decision 5) — no concrete caller yet; the same "guess now, in a file nobody asked to guess in" mistake M1's ADR already named and avoided for `Provenance.tier`.
- A flat `forget(memory, reason, now, supersededBy?)` signature with only a runtime check (Decision 6) — reopens, one layer below, the exact gap M1's own `Tombstone` split already closed at the type level.
- `node:crypto`'s `randomUUID` for `TombstoneId` minting (Decision 7) — needs an import this milestone's own frozen architecture boundary would have to special-case, for a property (unpredictability) this identity does not need.
